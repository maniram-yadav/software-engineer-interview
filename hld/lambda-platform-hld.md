# Serverless Function-as-a-Service Platform (AWS Lambda-style) — High-Level Design

**Assumed metrics**: multi-tenant platform serving many thousands of customers · aggregate peak invocations in the low tens-of-millions/sec across the fleet · per-function concurrency bursts from 0 to thousands of simultaneous executions in seconds · cold-start target: low hundreds of ms for interpreted runtimes, faster for compiled; warm-invoke overhead target: single-digit ms · execution timeout ceiling in the minutes range · strict multi-tenant security isolation (this is the platform's single hardest constraint, discussed throughout).

**Scope, explicitly enumerated**: function packaging/deployment (code + config, versions/aliases) · synchronous invocation (a caller waits for the response, e.g., fronted by an API Gateway) · asynchronous invocation (fire-and-forget with retry/DLQ semantics, e.g., triggered by a storage event) · poll-based stream/queue event sources (the platform itself polls a queue/stream and invokes the function with batches) · elastic, per-function auto-scaling from zero to high concurrency · strong isolation between tenants sharing physical hardware · observability (logs/metrics/traces) and usage-based billing.

This is a different problem shape from every other system in this thread: it's not "route/store/analyze data for an application," it's **a multi-tenant compute scheduler that must start a stranger's arbitrary code, in complete isolation from every other stranger's code, in well under a second, thousands of times a second, on shared physical hardware.** The central engineering tension — instant elasticity vs. strong isolation vs. cost efficiency — doesn't map cleanly onto any pattern used in the earlier designs and gets the bulk of the attention below.

# High-Level Design (HLD)

## 1. Scope & System Estimation

**Functional Requirements**
- Accept a function's code package (zip or container image) plus configuration (memory, timeout, IAM execution role, environment variables, VPC settings, triggers) and store it durably, versioned
- Invoke a function synchronously and return its result to the caller, transparently starting a new execution environment ("cold start") when no idle one is available, or reusing one ("warm start") when possible
- Invoke a function asynchronously in response to an event, with automatic retry on failure and a dead-letter destination after retries are exhausted
- Continuously poll external event sources (queues/streams) on the customer's behalf and invoke the function with batches of records, tracking read position per source
- Scale the number of concurrent executions for a given function up and down automatically, per-function, with no pre-provisioning required by default
- Strongly isolate each execution — one customer's function must never be able to observe, affect, or steal resources from another's, even though many run on the same physical host
- Enforce configured resource limits (memory, CPU proportional to memory, execution timeout) and terminate/bill accordingly
- Emit logs, metrics, and traces per invocation for observability and per-invocation billing

**Non-Functional Requirements**
- **Isolation is the non-negotiable, above even availability or latency** — a security boundary failure between tenants is a platform-ending event in a way that a slow invoke or even a failed invoke isn't; every architectural choice here is shaped by "how do we get near-VM-grade isolation at container-grade speed and density."
- Latency: cold start should be minimized aggressively (it's the single most product-visible weakness of any FaaS platform) while warm-path overhead should be near-zero compared to the customer's own code execution time
- Availability: the invoke path (control plane accepting a call, data plane executing it) needs very high availability, since it's synchronously on the critical path of whatever application is calling it
- Elasticity: must scale a single function from zero to very high concurrency within seconds of a demand spike, without the customer having to provision anything in advance (the entire value proposition of "serverless")
- Multi-tenancy efficiency: the economics of the whole platform depend on packing many customers' idle-most-of-the-time functions densely onto shared hardware — a platform that isolated tenants by giving each a permanently dedicated VM would not be a serverless platform at all, just VMs with extra steps

**Back-of-the-Envelope Estimation**
- Fleet-wide peak of low tens-of-millions of invocations/sec, but any single function's traffic is typically a tiny, bursty slice of that — the scaling problem is fundamentally **per-function elasticity**, not "one big load-balanced pool"; a viral spike on one customer's function must scale that function's concurrency without being throttled by or competing unfairly against every other tenant's baseline load.
- Cold-start budget: if a request-response invoke needs to feel "instant," a cold start needs to complete (provision isolated sandbox + load code + initialize runtime + run the customer's init code) within roughly one to a few hundred milliseconds for it to be broadly acceptable — this single number is what rules out "just start a full VM per invocation" (VM boot times are seconds, not milliseconds) and is the reason a **lightweight virtualization layer**, not a full traditional VM and not a bare container, is the architectural answer (detailed in §2).
- Idle-capacity economics: at any given moment, the overwhelming majority of a platform-wide fleet of provisioned execution environments are idle (most functions are invoked sporadically, not continuously) — this is why execution environments are **reused across sequential invocations of the same function** (kept warm for a window after finishing, then reclaimed) rather than torn down instantly, trading a small amount of idle-resource cost for eliminating most cold starts under sustained, if not perfectly steady, traffic.
- Poller fan-out: for stream/queue-based triggers, the platform itself runs the equivalent of one lightweight polling worker per (customer, event-source) pair across potentially millions of configured triggers — this is a separate, much smaller-footprint scaling problem than raw invocation throughput, since a poller is idle most of the time and only triggers invocations when it finds records.

## 2. System Architecture & Components

**Architecture Style**: A sharp split between a **Control Plane** (function definitions, configuration, deployment — infrequent, can tolerate more latency, needs to be highly consistent about "what does this function's current config say") and a **Data Plane** (the actual invoke-and-execute hot path — extremely frequent, must be fast, and is where the isolation and elasticity problems actually live). This mirrors the control-plane/data-plane split used for the load balancer and API gateway designs earlier in this conversation, but the data plane here is solving a fundamentally harder problem than "forward a request to a healthy backend" — it's **provisioning and tearing down isolated compute itself**, on demand, per invocation.

**Component Breakdown**
- **Function Registry / Control Plane API**: accepts function creation/update calls, stores code packages (in durable object storage) and configuration (memory/timeout/role/triggers/env vars), manages versions and aliases (e.g., a `prod` alias pointing at version 12)
- **Invoke Frontend**: the entry point for synchronous invokes — authenticates the caller, resolves which function/version/alias is being invoked, and hands off to the Placement/Scheduling layer to get an execution environment
- **Placement & Scheduling Service**: the core elasticity brain — for a given invoke request, decides whether an existing idle, warm execution environment for this exact function+version can be reused, or whether a new one must be provisioned (cold start), and on which physical host in the fleet there's capacity
- **Worker Fleet (hosts running the isolation layer)**: physical (or hypervisor-level) machines, each capable of hosting many lightweight, hardware-virtualized micro-VMs, each micro-VM running exactly one customer's execution environment at a time — this is where the isolation-vs-density tension is actually resolved, detailed in §4
- **Execution Environment**: the actual sandboxed runtime instance — customer code, language runtime, and a thin invoke-handling shim, running inside one micro-VM; can be frozen (paused) between invocations rather than torn down, to serve a subsequent invoke of the same function without paying cold-start cost again
- **Async Invocation Queue**: for asynchronously-triggered invokes (e.g., a storage event), the event is durably enqueued first, decoupling "the event happened" from "the function actually ran" — enables retry-with-backoff and eventual dead-lettering, without the event source ever needing to know or care about function-side failures
- **Event Source Poller Fleet**: a separate, much lighter-weight fleet of workers that continuously poll external queues/streams on the customer's behalf, tracking read position (offset/sequence number) per source, and translate "new records available" into invoke calls with batches of records
- **Code/Layer Store**: durable, versioned storage (object storage) for function code packages and shared "layers" (reusable dependency bundles merged into the execution environment at cold-start time)
- **Metering & Billing Pipeline**: records duration × memory (and request count) per invocation, aggregated for usage-based billing — a streaming aggregation job, structurally similar to every usage-metering component in the earlier designs in this conversation
- **Observability Pipeline**: per-invocation logs, metrics, and distributed traces, correlated by invocation ID

**Data Flow Walkthrough**

*Synchronous invoke path:*
1. Caller (e.g., an API Gateway, or a direct SDK call) sends an invoke request for `functionName` (or a specific version/alias) with a payload.
2. Invoke Frontend authenticates the call and resolves the function's current code reference and configuration.
3. Placement & Scheduling Service checks for an existing **warm, idle execution environment** for this exact function+version. If found: hand the invoke directly to it (warm start — fast path, no provisioning needed). If not found: provision a fresh micro-VM on a worker host with capacity, load the function's code and layers into it, initialize the runtime and run the function's init code (cold start — slow path).
4. The execution environment runs the customer's handler function against the payload, within its configured memory/timeout limits.
5. Result is returned back up through the Invoke Frontend to the caller; the execution environment is **not torn down immediately** — it's kept warm for a window in case another invoke for the same function arrives soon (this is the single biggest lever on average-case latency for bursty-but-not-constant traffic).
6. Metering pipeline records the invocation's billed duration and memory; observability pipeline records logs/metrics/trace for this invocation ID.

*Asynchronous invoke path:*
1. An event source (e.g., a storage event) triggers an async invoke — the event is durably enqueued immediately, and the caller/event-source's job is done at that point (no waiting for the function to actually run).
2. A separate consumer pulls from the Async Invocation Queue and performs the same placement/execute flow as the synchronous path, but the *caller* is the queue consumer, not the original event source.
3. On failure, the invoke is retried with backoff, up to a configured retry limit; if still failing, the event is routed to a configured dead-letter destination rather than being silently dropped — this is the same "never silently lose the thing, make failure visible and actionable" principle used in the file-upload service's fail-closed quarantine and the banking design's fail-closed fraud-hold posture, applied here to a failed function execution instead of a security risk.

*Stream/queue-triggered path:*
1. Event Source Poller Fleet continuously polls the configured external source (a queue or stream) on the customer's behalf, tracking its own read position per source.
2. When new records are available, the poller batches them (up to a configured batch size) and issues what is effectively a synchronous invoke of the customer's function with that batch as the payload.
3. On success, the poller advances its tracked read position; on failure, behavior depends on configuration (retry the batch, skip and move on, or route to a failure destination) — this is deliberately configurable because "what should happen to unprocessed stream records" has genuinely different correct answers depending on the customer's use case (some want at-least-once retry-until-success, others want to never block the stream on one bad record).

## 3. Storage & Data Strategy

**Database Selection**
- **Code/Layer Store**: durable object storage — code packages are immutable once published (a new deployment is a new version, never an overwrite of an existing one), which maps naturally onto object storage's strengths and is also what makes versioning/rollback safe and simple.
- **Function configuration / Control Plane metadata**: a strongly consistent store — a function's current configuration (which version an alias points to, memory/timeout settings) needs to be read reliably and correctly by every invoke, since serving an invoke against stale config (e.g., an old IAM role) would be a real correctness and security problem, not just a UX nicety. This is one of the few genuinely CP-leaning pieces of this design.
- **Placement/scheduling state** (which hosts have capacity, which execution environments are currently warm-and-idle for which function): a fast, high-throughput, AP-leaning store — this is conceptually the same role as the load balancer design's target registry and the chat app's session registry, here tracking "warm execution environment location" instead of "healthy backend" or "connected socket," and it's fine for this view to be briefly stale (worst case: an avoidable cold start where a warm environment existed but wasn't found in time — a performance cost, not a correctness one).
- **Async invocation queue**: a durable, ordered-enough message queue — durability here plays the same "never silently lose the thing" role as the durable event log in the chat and loyalty designs, applied to pending function invocations instead of chat messages or business events.
- **Metering data**: an append-only event stream aggregated by a downstream batch/streaming job into per-customer usage totals — same shape as the API gateway's usage/metering pipeline and the loyalty platform's event aggregation.

**Data Lifecycle**
- **Execution environment warm-window**: after completing an invoke, an environment is kept alive and frozen for a bounded idle window (long enough to catch the common case of "another invoke arrives soon," short enough to reclaim capacity from genuinely idle functions) — this single tunable is the primary lever balancing cold-start frequency against fleet-wide resource efficiency, and it's the direct FaaS analog of connection pooling in a traditional client-server system.
- **Code versioning**: every deployment creates a new immutable version; aliases (e.g., `prod`, `staging`) are mutable pointers to a version — this is what makes safe rollback trivial (repoint the alias) without ever needing to "undo" a deployment in place, the same "reversal, not edit" philosophy used for corrections in the banking ledger design, applied here to code deployments instead of financial transactions.
- **Poller checkpoint/offset tracking**: persisted per (customer, event source) pair so a poller restart (host failure, rebalancing) resumes from the last successfully-processed position rather than reprocessing everything or skipping records — same checkpointing discipline as any durable stream-consumer design.
- **Cold host/environment reclamation**: idle worker-host capacity is continuously rebalanced across the fleet (consolidating sparse idle environments to free up whole hosts, or spreading load to avoid hot spots) as a background process, decoupled from the invoke-time hot path.

## 4. Cross-Cutting Concerns & Trade-offs

**CAP Theorem & Trade-offs**
- Function configuration (control plane): **CP-leaning** — an invoke must use the currently-correct configuration (especially the IAM execution role, which is a security boundary, not just a setting), so this specific piece of metadata is worth the extra consistency cost even though most of the rest of this platform leans AP.
- Placement/scheduling state (which environments are warm, which hosts have room): **AP** — a stale view here just costs an avoidable cold start, never a correctness violation, so it's optimized for speed and availability over strict consistency, the same reasoning as every "routing table"-shaped component in this conversation (the LB's target health, the gateway's route config, the chat app's session registry).
- Async invocation queue: durability trumps strict ordering guarantees in the general case — retries and dead-lettering are explicitly designed around "this will sometimes be at-least-once, sometimes out of the customer's control over ordering," and customers who need strict ordering are expected to use a stream-based trigger (which does track position) rather than the async invoke path.

**Resiliency & Security — this is where the actual hard problem of the whole platform lives**
- **The isolation mechanism is the platform's core security boundary, and it's solved by lightweight, hardware-virtualized micro-VMs, not plain OS containers.** Plain containers (shared kernel) are fast to start but don't provide strong enough isolation between mutually-untrusting tenants sharing a host — a container escape is a full host compromise across every tenant on it. A traditional full VM per invocation would be isolated enough but far too slow to start (seconds, not the milliseconds this platform's cold-start budget demands) and too resource-heavy to run at the density the economics require. The answer this class of system uses is a **minimal, purpose-built virtual machine monitor** running lightweight micro-VMs — each tenant's execution environment gets true hardware-virtualization-backed isolation (its own kernel, its own memory space, no shared-kernel attack surface with any other tenant) while booting in tens of milliseconds rather than seconds, because the micro-VM's device model is deliberately minimal (none of a traditional VM's legacy hardware emulation) — this is the specific architectural choice that resolves the "instant elasticity vs. strong isolation" tension called out in the introduction, rather than treating it as an unsolvable trade-off.
- **Resource limits enforced at the hypervisor level, not just the application level**: memory and CPU are hard-capped per micro-VM by the virtualization layer itself, and execution timeout is enforced by force-terminating the environment — a runaway or malicious function cannot starve other tenants' resources on the same host, because the isolation boundary is below the OS, not just a process-level cgroup.
- **Network isolation**: each execution environment gets its own isolated network namespace; functions configured to run inside a customer's private network (VPC) get connectivity brokered through a controlled path rather than direct host-network access.
- **Fail-safe on placement failure**: if no worker host has capacity for a new cold-start environment, the platform must fail the invoke cleanly (a clear throttling error) rather than degrade isolation guarantees to squeeze in one more tenant — this is the FaaS-platform analog of the banking design's "never trade correctness for availability," applied to isolation instead of balance correctness.
- **Per-invocation credential scoping**: each execution environment is granted only the specific IAM permissions configured for that function, scoped to that invocation's lifetime — no execution environment retains broader access than the function it's running, and no environment is ever reused across different customers' functions, even briefly, even under extreme load.
- **Reused-environment state hygiene**: because environments are kept warm and reused across sequential invokes of the *same* function, any in-memory state left over from a prior invoke is visible to the next one *for that same customer's function* — this is a documented, accepted behavior (functions are expected to be written defensively about this), not a security issue, since warm reuse never crosses tenant boundaries; but it is a real correctness gotcha customers need to design around (e.g., not assuming a fully clean slate on every invoke).

---

### Key design decisions worth flagging back to you
1. **The lightweight-micro-VM isolation layer is the single decision the entire platform's economics and trust model rest on** — it's specifically what makes "strong VM-grade isolation" and "container-grade startup speed and density" simultaneously achievable, rather than a trade-off the platform has to pick a side of.
2. **Warm-environment reuse is the primary lever against cold-start latency**, and it's the direct FaaS analog of connection pooling — the same idea (keep expensive-to-create resources around briefly rather than always paying setup cost) recurring in yet another domain in this conversation.
3. **The control/data-plane split here is doing more work than in the LB or API Gateway designs**, because the data plane isn't just routing to existing capacity — it's dynamically provisioning and tearing down the capacity itself, per invocation, which is the genuinely novel hard problem this whole design exists to solve.
